## Summary
Jenkins detected the new commit (it polls every 2 minutes) before the Jenkins container had been rebuilt with Python.
The pipeline ran on the old Jenkins and failed with `python3: not found`.

## Evidence
- Build #2 started at 12:17 ("Started by an SCM change"); the Jenkins rebuild finished at 12:19.
- `docker exec qa-lab-jenkins python3 --version` after the rebuild → `Python 3.13.5`.

## Analysis and resolution
A race condition between the infrastructure update and the automatic trigger. It is not a code defect:
build #3, on the updated Jenkins, passed with no changes.
Process resolution (README, update section): update the tools first (`docker compose up -d --build`)
and only then make the commit available; if the infrastructure fails, use **Restart from Stage** or a new build.

## Reopened (build #4) and technical fix
The defect **happened again** in build #4: Jenkins was restarted in the middle of `docker build` (exit -1).
The process rule was not enough: it depended on someone remembering the right order.

Technical fix (v0.5.0):
- `scripts/jenkins_ctl.py` puts Jenkins in **quiet down** (it starts no new builds) and waits for running builds
  to finish (up to 10 min).
- `scripts/update_tools.ps1 -PauseOnly` pauses before the new code comes in; without `-PauseOnly`, it pauses (if needed),
  rebuilds and restarts Jenkins, which then accepts builds again.

Lesson: a defect that comes back after a "process" fix needs a fix that makes it impossible.
