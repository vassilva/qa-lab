# DEF-013 · QA integrity queries still join tables that now live in different databases

| Field | Value |

## Summary
In v0.5.0 Settlement became a separate service with its own database (`settlement`). The QA query file
still joined `trades` (Trading database) with `settlement_instructions` (Settlement database) and read the business date
from the Trading `system_state`. Run against the Trading database, the file stopped at the first of those queries.

## Steps to reproduce
1. In the QA Trading container: `psql "$DATABASE_URL" -f db/consultas_qa.sql`.

## Expected result
Every query runs; integrity checks return 0 rows when the data is consistent.

## Actual result
```
psql:db/consultas_qa.sql:30: ERROR:  relation "settlement_instructions" does not exist
```

## Analysis
An architecture change (one database → one database per system) that was not carried through to the QA tooling.
The automated tests did not catch it because none of them runs this file. No impact on the product, but the
integrity checks — the evidence used in defect analysis — were silently broken.

## Fix
- `db/qa_queries.sql`: only Trading tables, plus a new check for trades whose event was never published (outbox).
- `db/qa_queries_settlement.sql` (new): Settlement checks, including "at most one instruction per trade" (idempotency).
- Checks across the two databases are done by `GET /api/reconciliation`, which is covered by BDD (AC-L05, AC-I01, AC-I04).

## Retest
Both files run on PostgreSQL with no errors (`psql -v ON_ERROR_STOP=1 -f ...`).

## Prevention
When the architecture changes, review the QA tooling (queries, scripts, presets) as well as the code and the tests.
