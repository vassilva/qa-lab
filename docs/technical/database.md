# Databases in the QA Lab

Each environment has its own PostgreSQL 15 server (`qa-lab-qa-db`, `qa-lab-uat-db`) with **two databases**, one per system:
`qa_lab` (Trading, schema `db/schema.sql`) and `settlement` (Settlement, schema `db/schema_settlement.sql`).
Settlement never reads the Trading database: trades reach it as Kafka messages, as between separate systems.

## How to access

| Where | How |
| --- | --- |
| Environment terminal | `psql "$DATABASE_URL"` (in `qa-lab-qa-app` it is `qa_lab`; in `qa-lab-qa-settlement` it is `settlement`) |
| Adminer (`localhost:8081`) | System PostgreSQL · server `qa-lab-qa-db` or `qa-lab-uat-db` · `qa` / `qa` · database `qa_lab` or `settlement` |
| VS Code or DBeaver on your PC | `localhost:5433` (QA) or `localhost:5434` (UAT) · `qa` / `qa` · `qa_lab` or `settlement` |
| The page's SQL console | Read-only (the application refuses INSERT, UPDATE and DELETE); choose the Trading or Settlement database |

## Data model

| Database | Table | Key | Relations and rules |
| --- | --- | --- | --- |
| qa_lab | `orders` | `order_id` | `side` only BUY/SELL (CHECK); `price` NULL = market order |
| qa_lab | `trades` | `trade_id` | `buy_order_id` and `sell_order_id` → `orders` (FOREIGN KEY); `qty > 0` (CHECK) |
| qa_lab | `outbox_events` | `event_id` | Event stored in the same transaction as the trade; `published_at` NULL = not yet sent to Kafka |
| qa_lab | `system_state` | `state_key` | Environment generation (increases at every test reset) |
| settlement | `settlement_instructions` | `instruction_id` | `trade_id` **UNIQUE** (at most 1 instruction per trade: idempotency); `status` only PENDING/ON_HOLD/FAILED/SETTLED |
| settlement | `rejected_events` | `id` | Messages that broke the contract (also in the `trades.executed.dlq` topic) |
| settlement | `system_state` | `state_key` | System business date |

## Schema migrations

Each service creates its missing tables at startup (`db/schema.sql`, `db/schema_settlement.sql`), but creating is not
enough when a version **removes or changes** structure. Those changes are numbered SQL files in `db/migrations/<database>/`
(`trading/`, `settlement/`), applied once each at startup and recorded in the `schema_migrations` table.

| Check | How |
| --- | --- |
| Which migrations ran | `SELECT * FROM schema_migrations;` (in each database) |
| Does the database have exactly the expected tables? | `GET /health` → `schema_ok`, `unexpected_tables`, `missing_tables` (also checked by the smoke test) |

Example: `trading/001_drop_legacy_settlement_instructions.sql` removed a table left behind in `qa_lab` when Settlement
moved to its own database in v0.5 (DEF-016).

## QA queries

| File | Database | Contents |
| --- | --- | --- |
| `db/qa_queries.sql` | qa_lab | 7 queries: overview, rejections, VWAP, order book, and 3 integrity checks (executed quantity, trade price, events not published) |
| `db/qa_queries_settlement.sql` | settlement | 7 queries: instructions by status, overdue, failed/recycling, calendar, DLQ, and 2 integrity checks (settled early, duplicates) |

Integrity checks must return **0 rows**. Checks that need both databases (every trade has an instruction with the same amount)
are done by the API: `GET /api/reconciliation` (button **Reconcile systems** on the page). See DEF-013 for why.

Validated on PostgreSQL with 300 orders generated by `scripts/generate_orders.py`:

| Check | Correct data | Challenge mode |
| --- | --- | --- |
| Trading 4 · Executed quantity ≠ order (DEF-003) | 0 | **13 orders** |
| Trading 5 · Price ≠ resting order's price (DEF-002) | 0 | **117 trades** |
| Settlement 2 · Settled before the intended date | 0 | 0 |
| Settlement 3 · More than one instruction per trade | 0 | 0 |

Run everything: `psql "$DATABASE_URL" -f db/qa_queries.sql` (Trading container) and
`psql "$DATABASE_URL" -f db/qa_queries_settlement.sql` (Settlement container).

## Exercises

1. How many orders are there by status? And by symbol and side? *(GROUP BY with two columns)*
2. What is the difference between `INNER JOIN` and `LEFT JOIN` in Trading check 6? Why must it be LEFT? *(INNER would hide trades without an event)*
3. Why does Trading check 4 repeat the expression in `HAVING` instead of using the `executed` alias? *(see DEF-010)*
4. Try `INSERT INTO trades ...` with a `buy_order_id` that does not exist. Which error do you get and why? *(foreign key)*
5. In the settlement database, try to create a second instruction for the same trade. *(UNIQUE constraint: protection against settling twice)*
6. Inside `BEGIN; DELETE FROM settlement_instructions; SELECT count(*) ...; ROLLBACK;`, what happens to the data? *(transactions)*
7. Write a query with the VWAP by symbol on the last trading day. *(starting point: Trading query 3)*
8. Which index helps the end of day find the due instructions? *(`idx_si_status_isd`; try `EXPLAIN` on the EOD query)*
9. Why can't one SQL query join `trades` and `settlement_instructions` any more? How do real systems reconcile then? *(separate databases; reconciliation through APIs or files)*
10. Make a backup (`scripts/backup_db.sh`) and restore it into a new database:
    `psql "$DATABASE_URL" -c "CREATE DATABASE restore_test"` and then `gunzip -c <file> | psql "${DATABASE_URL%/*}/restore_test"`.
11. Difference between `DELETE`, `TRUNCATE` and `DROP`: try it on a restored copy, never in UAT.
