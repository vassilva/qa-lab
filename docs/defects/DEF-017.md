# DEF-017 · Order with an invalid side returns HTTP 500, exposes database details and is not persisted

| Field | Value |
| --- | --- |
| Status | Fixed (in retest) |
| Component | Order Entry Gateway / Database (orders persistence) |
| Severity | Medium |
| Priority | P2 |
| Environment | QA · normal mode |
| Version | 0.6.4-734df4b |
| Acceptance criterion | AC-L01 (invalid orders are rejected with a reason) |
| Risk | Input validation · audit trail · information disclosure |
| Detected by | Exploratory negative API test (Postman) |
| Date | 2026-11-04 |

## Summary
An order with an invalid `side` (empty, or any value other than `BUY`/`SELL`) is correctly rejected by the
Order Entry Gateway, but saving the rejected order fails on the database constraint `orders_side_check`.
The API answers **500 Internal Server Error** instead of **422**, the response exposes internal database details,
and the rejected order exists in memory but **not** in the database.

## Steps to reproduce
1. QA environment, after `POST /api/reset`.
2. `POST {{trading_url}}/api/orders` with body
   `{"symbol": "GALP", "side": "", "qty": 10, "price": 15.2}`

## Expected result
- HTTP **422**, order `status: REJECTED`, `reject_reason: "Invalid side"` (same behaviour as other invalid orders,
  e.g. price outside bands).
- The rejected order is stored in the `orders` table for audit.
- No internal details (tables, constraints, SQL) in the response.

## Actual result
- HTTP **500**:
  `"Internal error: new row for relation \"orders\" violates check constraint \"orders_side_check\" DETAIL: Failing row contains (O000002, GALP, , 10, 15.2000, 10, REJECTED, Invalid side, ...)"`
- Memory and database disagree (see evidence).

## Evidence (API, SQL)
| Source | O000002 |
| --- | --- |
| `GET /api/orders` (Matching Engine memory) | present · `side: ""` · `REJECTED` · `Invalid side` |
| `POST /api/query` → `SELECT ... FROM orders` (database `qa_lab`) | **absent** (only O000001) |
| `GET /api/integration` | outbox 0 · consumer healthy · `schema_ok: true` (no side effect on integration) |

Code review: any value outside BUY/SELL (e.g. `"HOLD"`, `"X"`) takes the same path; to be confirmed in the retest.

## Analysis
- **Severity Medium:** no trade is executed and no money is affected, but three problems combine:
  wrong error contract for API clients (500 vs 422), **information disclosure** (table and constraint names, row data),
  and **lost audit trail** (rejected order disappears after a restart, memory ≠ database).
- **Root cause:** the database rule `CHECK (side IN ('BUY','SELL'))` is stricter than the rejected-order path.
  The gateway saves every order, valid or rejected, and a rejected order can carry an invalid side.
  The generic error handler returns the raw exception text to the client.
- **Why tests missed it:** the negative tests covered quantity, price, tick size and symbol, but not `side`
  (equivalence class "invalid side" not in the test design).

## Fix (v0.6.5)
Decision: an invalid side is a **business rejection** (contract: 422 "Rejected by the gateway rules"), so the order
is kept for audit with the value it was sent with. A value that cannot even be stored is a **malformed request** (400).

1. **Database:** `orders.side` accepts any value up to 10 characters for REJECTED orders only:
   `CHECK (side IN ('BUY','SELL') OR status = 'REJECTED')`. Accepted orders are still BUY or SELL.
   Migration `trading/002_allow_invalid_side_on_rejected_orders.sql` (PostgreSQL; on SQLite the fresh schema already
   has it, the migration is only recorded).
2. **API format limits** (`_parse_order`): symbol or side longer than 10 characters, quantity beyond INTEGER,
   price beyond NUMERIC(12,4) → **400 Invalid request**, no order created. Same family of defect: these values
   would also have crashed the insert with 500.
3. **Error handler:** a 500 now returns only `{"error": "Internal error", "error_id": "..."}`; the details are in
   `qa-lab.log` with the same `error_id`, so support can find them without exposing them.
4. **Regression tests** (`tests/api/test_order_input_validation.py`, 10 tests + 1 migration test):
   invalid side `""`, `HOLD`, `X`, `BUYY` → 422 and present in memory **and** database · lowercase `sell` still
   accepted · oversized values → 400 and nothing stored · a forced internal error does not leak details.

## Retest (QA, after the pipeline deploys 0.6.5)
1. Trading log: `[DB] Migration 002_allow_invalid_side_on_rejected_orders applied`.
2. Postman: `POST /api/orders` with `"side": ""` → **422**, `REJECTED`, `Invalid side`.
3. `GET /api/orders` and `SQL · Trading: ordens` → the rejected order is in **both**.
4. `"side": "BUY-AND-HOLD"` (12 characters) → **400** `Invalid request`, no new order.
5. Regression: the normal GALP sell + buy still gives 201 and a trade.

## Lesson
Negative tests must cover **every input field**, not only the obvious ones (here quantity and price were covered,
side was not). And a rejection path also writes data: test that it can be stored, not only that it is refused.
