# DEF-016 · Orphan `settlement_instructions` table left in the Trading database after Settlement became a separate service

| Field | Value |
| --- | --- |
| Status | Closed |
| Component | Database / Deployment (schema upgrade) |
| Severity | Low |
| Priority | P3 |
| Environment | QA and UAT upgraded from v0.4 (does not happen on a fresh install) |
| Version | 0.6.3-bd6f5be |
| Acceptance criterion | — |
| Risk | T-02 |
| Detected by | Manual investigation (tracing a failed EDP settlement in DBeaver) |
| Date | 2026-11-03 |

## Summary
Until v0.4 the settlement instructions lived in the Trading database (`qa_lab`). In v0.5 Settlement became a separate
service with its own database (`settlement`). The startup code only **creates** missing tables, it never **removes**
tables that are no longer used, so environments upgraded from v0.4 kept an old, unused `settlement_instructions`
table in `qa_lab`, with the same name as the real one in `settlement` but a different structure.

## Steps to reproduce
1. Use an environment that was first deployed with v0.4 and later upgraded to v0.5 or above.
2. In a SQL client connected to the **Trading** database (`qa_lab`), run
   `SELECT instruction_id, event_id FROM settlement_instructions;`

## Expected result
`ERROR: relation "settlement_instructions" does not exist`: the table only exists in the `settlement` database.

## Actual result
`ERROR: column "event_id" does not exist`: the table exists in `qa_lab` with the old structure.
`SELECT COUNT(*) FROM settlement_instructions;` in `qa_lab` returns 0.

## Analysis
- Severity **Low**: the table is empty and not used by any service. The risk is misleading investigations:
  a query on the wrong database returns 0 rows instead of a clear error. (Initially estimated Medium; lowered
  after confirming the table had no data.)
- Root cause: a schema change (moving a table to another database) shipped without a **migration** to remove the
  old structure. Not caught because the tests check what the system does, not that the database has exactly the
  expected tables, and the pipeline does not test the **upgrade path**.

## Fix
- Numbered SQL migrations in `db/migrations/<database>/`, applied once at service start and recorded in a new
  `schema_migrations` table (kept on reset). Migration `trading/001_drop_legacy_settlement_instructions.sql`.
- `/health` of Trading and Settlement reports `schema_ok`, `unexpected_tables` and `missing_tables`
  (expected = tables in the schema file).
- `scripts/smoke.sh` fails if either database has unexpected or missing tables.
- Tests: `tests/unit/test_migrations.py` (fresh install, upgrade from v0.4, run-once, leftover detection).

## Retest
Next deployment to QA and UAT: the Trading log shows `[DB] Migration 001_drop_legacy_settlement_instructions applied`,
the smoke shows "database schemas as expected", and the query above returns *relation does not exist*.

## Lesson
Test the upgrade path, not only fresh installs: some defects only exist in environments that have history.
