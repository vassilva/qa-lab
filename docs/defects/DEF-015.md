# DEF-015 · BDD starts before the Settlement Kafka consumer is ready after a redeploy (intermittent failure)

| Field | Value |

| Severity | High |
| Priority | P1 |
| Environment | QA (Kafka) |

| Acceptance criterion | AC-L01 (first scenario that needs Settlement) |
| Risk | T-05, R-16 |

| Date | 2026-11-03 |

## Summary
After each deployment the Settlement container is recreated and its Kafka consumer must join the group
`settlement-service`. Kafka only assigns the partition to the new consumer after the old one (from the previous
container, stopped without leaving the group) is declared dead. During that time Settlement is *up* but cannot
receive trades. The smoke test only checked that Kafka answered, so the BDD regression started too early and the first
settlement scenario waited 15 s for an instruction that had not arrived yet.

## Evidence
- Build #10: `03_settlement.feature F........`, the first example took ~25 s, then all the other scenarios passed.
- Build #9 (same code path): the same feature took 14 s and passed just under the 15 s limit: the problem was
  already there, intermittently.
- Only the first scenario needing Settlement is affected; trades created later are delivered normally.

## Analysis
Liveness is not readiness. `healthy` meant "the HTTP service answers", not "the consumer can receive messages".
A typical pitfall with Kafka consumer groups after a redeploy (rebalance / session timeout).

## Fix
- `app/bus.py`: the Kafka consumer reports ready only when the group coordinator assigns it the partition
  (rebalance listener); session timeout lowered to 6 s so the old consumer expires faster.
- Settlement `/health` exposes `consumer_ready`.
- `scripts/deploy.sh` waits (up to 90 s) for `consumer_ready` before declaring the environment ready.
- `scripts/smoke.sh` fails if the consumer is not ready; the BDD `before_all` also waits for it.
- New test `test_kafkabus_only_ready_after_partition_assignment` (fake Kafka consumer).

## Retest 1 (build #11): failed → reopened
`scripts/deploy.sh: line 56: jq: command not found` for 90 s, then "the Settlement consumer has no Kafka partition".
The readiness check piped the output into `jq` **in the Jenkins container**, where `jq` is not installed
(it only exists in the application image). It worked on the development machine, which has `jq`.
Fix: the whole check runs inside the Settlement container (`docker exec … sh -c 'curl … | jq …'`), and the error
message now shows the Settlement application log. Simulated with a host where `jq` does not exist.

## Retest 2
Next build: "Settlement consumer ready (Ns)" in the deploy log, smoke shows "consumer ready", 33/33 scenarios.

## Lessons
- For asynchronous integrations, a deployment is finished when the system can do its job, not when the process starts.
- Test a script where it really runs: a pipeline script runs on the CI agent, with the CI agent's tools.
